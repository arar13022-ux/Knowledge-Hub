# KnowledgeHub — Architecture & Product Specification

## 1. Purpose

KnowledgeHub is an internal knowledge management platform for retail operations
teams. Agents on the floor or on the phone ask questions; the system answers
instantly from an approved knowledge base, and routes anything it can't answer
to a Subject Matter Expert (SME) or Admin for review. Every answer an agent
ever sees has been through a human approval step. Nothing is generated by an
external/unapproved AI model, and no confidential data leaves the system.

This document is the source of truth for engineering. The MVP scope in
Section 9 is what ships first; everything else is the roadmap.

---

## 2. Roles & Permissions

Three roles, enforced both in the UI and at the database layer via Postgres
Row Level Security (RLS) — never trust the client alone.

| Capability | Agent | Team Lead | Admin |
|---|---|---|---|
| Browse/search published KB articles (within their access group) | ✅ | ✅ | ✅ |
| Ask a question | ✅ | ✅ | ✅ |
| Give feedback (helpful / not helpful / report outdated) | ✅ | ✅ | ✅ |
| See own question history | ✅ | ✅ | ✅ |
| See team's unanswered/queued questions | ❌ | ✅ (own team) | ✅ (all) |
| Answer & submit a draft response | ❌ | ✅ | ✅ |
| Approve & publish a response | ❌ | ✅ (own team's SME queue) | ✅ |
| Create / edit / archive articles | ❌ | ✅ (draft only, needs Admin approval to publish) | ✅ |
| Manage categories, keywords, access groups | ❌ | ❌ | ✅ |
| Manage users & roles | ❌ | ❌ | ✅ |
| View analytics dashboard | ❌ | ✅ (team scope) | ✅ (global) |
| Configure review-date/aging policy | ❌ | ❌ | ✅ |

Access groups (e.g. "Store Ops", "E-commerce Fulfillment", "Loss Prevention")
scope *which* articles a user can see, independent of role. A Team Lead in
"Store Ops" cannot see "Loss Prevention" SME queues unless also granted that
group.

## 3. Core Data Model (Postgres / Supabase)

See `supabase/schema.sql` for the full DDL with RLS policies. Summary of
entities:

- **profiles** — extends `auth.users`; role, display name, team, avatar.
- **access_groups** / **profile_access_groups** — many-to-many scoping.
- **categories** — hierarchical (self-referencing `parent_id`).
- **keywords** — controlled vocabulary for matching.
- **articles** — the KB content. Always has a `status`
  (`draft` → `pending_review` → `published` → `archived`), `review_due_at`,
  `owner_id`, `access_group_id`.
- **article_versions** — full version history, immutable snapshots, diffable.
- **article_keywords** — many-to-many.
- **questions** — submitted by agents (via in-app form or Google Form sync
  webhook). Has `status`: `auto_answered`, `queued`, `answered`,
  `duplicate`.
- **question_matches** — the keyword/semantic match candidates the engine
  found for a question, with a confidence score, for transparency and audit.
- **answers** — SME/Admin-authored responses to a question, in a
  `draft` → `approved` → `published` workflow, always linked to source
  article(s).
- **feedback** — `helpful` / `not_helpful` / `outdated`, linked to an article
  or an answer.
- **notifications** — in-app (and optionally email) notices: "your question
  was answered," "an article you follow was updated," "SME queue item
  assigned to you."
- **audit_log** — append-only record of every publish, approval, role change,
  and deletion, for compliance.

All confidential-content protections live in RLS policies keyed off
`access_group_id`, so a leaked JWT or a client bug cannot expose out-of-scope
rows — the database itself refuses the query.

## 4. Question-Answer Matching Pipeline

This is intentionally **not** a black-box AI call — every match is
explainable and auditable, per the "no unapproved external AI" requirement.

1. **Normalize** — lowercase, strip stopwords/punctuation, expand a small
   internal synonym table (e.g. "POS" ↔ "point of sale").
2. **Keyword match** — look up `article_keywords` for exact/stemmed keyword
   hits; weight by keyword `priority`.
3. **Full-text search fallback** — Postgres `tsvector`/`ts_rank` over article
   title + body for partial matches when keyword overlap is weak.
4. **Score & threshold**:
   - Score ≥ high threshold → **auto-answer**: agent instantly sees the
     published article(s), each answer stamped "matched from approved
     source," with a still-visible "not what I needed" escape hatch.
   - Score in a mid band → show best-guess suggestions but **also** queue
     for human confirmation.
   - Score below threshold → **route to SME/Admin queue**, tagged with the
     detected category so it reaches the right team.
5. **Duplicate detection** — before queuing, check `questions` for
   near-identical normalized text within a rolling window; if found, link as
   a duplicate instead of creating a new queue item (feeds the "duplicate
   queries" analytic).

Because this is deterministic and rule-based, it can run entirely inside
Supabase (a Postgres function + a thin edge function), with no data ever
leaving the company's own infrastructure. Phase 2 can add an optional,
internally-hosted embeddings model behind the same interface if leadership
approves — the pipeline is designed so that swap doesn't change the UI
contract.

## 5. SME / Admin Review Workflow

```
Agent asks question
        │
        ▼
  Matching pipeline
   ├─ high confidence ─────────────► Agent sees answer instantly
   ├─ duplicate ───────────────────► Linked to existing thread, agent notified when resolved
   └─ low/no confidence ───────────► Queue (routed by category → team)
                                          │
                                          ▼
                                  Team Lead / SME drafts answer
                                          │
                                          ▼
                                  Admin (or Lead, if self-serve
                                  approval enabled for that team)
                                  reviews & approves
                                          │
                                          ▼
                          Published as answer + optionally
                          promoted into a new/updated KB article
                                          │
                                          ▼
                              Agent notified, feedback loop opens
```

Nothing reaches an agent as an "answer" without passing through the approve
step. Drafts are visibly marked as drafts to anyone with queue access.

## 6. Notifications

Triggered by Postgres triggers → `notifications` table → realtime channel
(Supabase Realtime) → toast + notification bell in the UI. Event types:

- Your question was answered.
- An article you bookmarked/follow was updated or is up for review.
- A queue item was assigned to you (Lead/Admin).
- An article you own is nearing its review-due date (aging topic alert).
- Feedback marked an article "outdated" (owner + Admin notified).

## 7. Analytics Dashboard

Metrics, computed via SQL views (materialized where needed for speed):

- **Unanswered questions** — count & trend, by category/team, with average
  time-to-answer.
- **Aging topics** — published articles past (or nearing) `review_due_at`,
  sorted by staleness and by traffic (so stale-but-popular sorts first).
- **Duplicate queries** — top clusters of duplicate/near-duplicate questions
  that never had a matching article — the clearest signal of a KB gap.
- **Feedback health** — helpful vs. not-helpful ratio per article; articles
  flagged outdated.
- **Queue throughput** — SME/Admin response SLA, backlog by team.
- **Search-miss report** — top searched terms that returned zero/low-score
  results.

Team Leads see their team's slice; Admins see everything.

## 8. Security & Compliance

- **Auth**: Supabase Auth (email/password + SSO/OIDC-ready for a corporate
  IdP in Phase 2). Session JWTs carry role + access groups as custom claims.
- **Authorization**: Postgres RLS on every table — enforced at the data
  layer, not just hidden in the UI.
- **No external AI leakage**: the matching pipeline is self-hosted logic
  (SQL + edge functions) using only company-approved content already in the
  KB. No third-party LLM API calls with company data are made anywhere in
  the MVP. If a future phase adds a generative layer, it must be an
  internally-vetted model, opt-in per access group, and never trained on
  private data.
- **Audit trail**: every publish/approve/role-change is written to
  `audit_log` (who, what, when, before/after).
- **Data minimization**: Google Form intake (if used) syncs only the
  question text + submitter email via a signed webhook — no other form
  metadata is stored.
- **Backups**: Supabase's point-in-time recovery; nightly export requirement
  documented for compliance sign-off.

## 9. MVP Scope (ship first)

1. Email/password auth with the 3 roles + access groups.
2. Knowledge base: categories, articles (create/edit/publish/archive),
   keyword tagging, version history, review-due dates.
3. Agent "Ask a question" page with instant matching (keyword + full-text).
4. Auto-route unmatched questions to the correct team's queue.
5. SME/Admin queue: draft → approve → publish workflow.
6. Notifications (in-app only for MVP; email is Phase 2).
7. Feedback buttons: helpful / not helpful / report outdated.
8. Analytics dashboard: unanswered count, aging topics, duplicate queries,
   feedback health.
9. Light/dark theme, responsive, accessible UI.

## 10. Roadmap (post-MVP)

- **Phase 2**: Google Form intake sync, email notifications, SSO/OIDC,
  bulk article import, per-team custom SLAs.
- **Phase 3**: Semantic search (internally hosted embeddings) layered under
  the same explainable-matching contract, article recommendation ("related
  articles"), Slack/Teams bot front-end for asking questions.
- **Phase 4**: Multi-language KB, mobile app wrapper, advanced permissions
  (per-article ACLs), scheduled review reminders with auto-escalation, full
  audit/compliance export reports.

---

## 11. Tech Stack

- **Frontend**: React 18 + TypeScript + Vite, Tailwind CSS, React Router,
  TanStack Query for data fetching/caching, Recharts for analytics.
- **Backend**: Supabase (Postgres, Auth, Realtime, Storage, Edge Functions).
- **Hosting**: static frontend on any CDN (Vercel/Netlify/internal), backend
  fully managed by Supabase (self-hosted Supabase is a drop-in option if
  data residency requires it).
- **CI/CD**: lint + typecheck + build on PR; migrations tracked in
  `supabase/migrations`.
